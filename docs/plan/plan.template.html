The product

SizJobs is a personal agent that finds jobs in Israel every morning that fit a move from DevOps to AI, explains why each one fits and what you are missing for it, and learns from your feedback. The interface is a single Telegram digest, in English.

Sources: LinkedIn job alerts from your mailbox, and a company list you build from LinkedIn. Microsoft's careers site joins in v0.2. Salary is out of scope for now. The product tasks themselves are in phase A5.

How we work on the project

The setup

VS Code, connected to WSL. The code, the tools and Claude Code all live inside WSL; VS Code on Windows is just the window into them. Install the Microsoft WSL extension in VS Code, and run code . from a WSL terminal in the project folder. Claude Code is installed inside WSL and runs in the VS Code integrated terminal, so you see its diffs in the editor as it works. Task p1-1 has the details.

Who does what

claude.ai chat

Planning a phase before you start, drafting ADRs, explaining anything unclear, and choices like which model to run.

Claude Code (local)

Most of the work: manifests, code, workflows, and Terraform in Part B. It runs in WSL with a read-only AWS profile, so it can run terraform plan but can't change anything in the cloud.

Claude Code (cloud)

At claude.ai/code. For side tasks that need neither the local cluster nor AWS, like the README, tests, Renovate config or the evals harness. It needs the Claude GitHub App on the repo. Runs in the background and opens a PR. Never give it AWS keys.

The loop for every task

  1. New branch: git switch -c p2-1-network
  2. Start Claude Code in plan mode: claude --permission-mode plan, and paste the task prompt.
  3. Read the plan it proposes and correct it before it writes a line. This is where you learn the most.
  4. It implements. You review the diff in VS Code, run pre-commit run -a, and check the change in the local cluster (in Part B, terraform plan).
  5. Open a PR with Closes #N, CI runs its checks, merge. In Part B, apply runs in CI.
  6. Tick the task here. If a decision was made, add an ADR.

The real safety boundary is IAM, not Claude Code. Locally you and Claude Code use a ReadOnly profile only, and in Part B cloud changes happen only through CI with OIDC. Deny rules in Claude Code are a convenient extra net, but per its own docs they are not a security boundary, since other forms of the same command can get around them. The one exception is the first apply of the persistent layer (b1-2, b1-3), which you run yourself.

Never paste secrets into any chat. In Part A they go into ~/.config/sizjobs/.env (a1-8), in Part B into SSM Parameter Store (b2-6), both straight from your terminal.

A public repo

  • Free where it matters. Actions on standard runners, public GHCR packages and GitHub Pages cost nothing, and rulesets protect main.
  • Everything is visible. Code, history, issues, PR comments and Actions logs. Secrets live only in the .env and in GitHub Secrets; personal data lives only in the private bucket.
  • Guardrails from the first commit. The .gitignore below (a1-2), gitleaks in pre-commit and CI (a1-7), and GitHub push protection.
  • No self-hosted runners, no pull_request_target. On a public repo both let a pull request from a fork reach your machine or your secrets.
  • Pages for the docs. The plan and product pages in docs/ can be served by GitHub Pages.

Build in parallel?

Not at first. Phases A1 and A2 are foundations everything depends on, so do them in order. From A3 there are three independent tracks:

Model and gateway

Phase A3, then A8. Local Claude Code, small and quick.

Product and agent

Phases A4 and A5. The main track, and the heart of the product.

Quality

Phases A6 and A7. The evals harness suits a cloud Claude Code session.

Two tracks in parallel is enough: one local and one in the cloud, or two local sessions on separate git worktrees. Beyond that you become the review bottleneck and reviews get shallow. Same for the agents themselves: first one agent working end to end with evals, then more agents or sources.

The goal is that you can explain every decision in an interview. Let Claude Code write the boilerplate: CI, pre-commit, Taskfile, Dockerfiles. For tasks marked learn deeply, write it yourself or go through every line, and ask Claude to explain rather than execute.

# sizjobs
SizJobs: a personal AI job-search agent (Hermes) on Kubernetes.
Part A (now): runs locally on k3d in WSL on a 16GB laptop with no GPU; the model is an API model behind LiteLLM.
Part B (later): the same platform on k3s in AWS eu-central-1, destroyed every evening and rebuilt in the morning.

## Layout
- platform/: ArgoCD app-of-apps and Helm values (local values, plus values-aws in Part B)
- services/: agent, mcp-tools (Python, uv)
- evals/: promptfoo configs and golden dataset
- infra/persistent, infra/ephemeral: Terraform, Part B only
- docs/: plan, product description, adr/ (one decision per file, Nygard format)

## Rules
- Code, comments, commits, issues and PRs are always in English.
- Keep every workload small: memory requests and limits on everything; the laptop gives WSL 10GB.
- Anything AWS-specific must have a local stand-in in Part A: MinIO for S3, the .env for SSM.
- Images: public GHCR from main, signed with cosign; the k3d local registry only for quick branch iteration.
- Never run terraform apply or destroy locally. CI applies on merge to main (Part B).
- Tag every AWS resource project=sizjobs and layer=persistent|ephemeral.
- Cost first: no NAT gateway, no ALB, no EKS. Flag anything that bills hourly.
- No secrets in git or in prompts. Locally they live in ~/.config/sizjobs/.env, on AWS in SSM.
- The repo is public: secrets and personal data (profile, company list, raw emails) never go into git, logs or PR comments.
- Never print secrets in workflows, never add self-hosted runners, never use pull_request_target.
- Run pre-commit run -a before you say a task is done.
- When you make an architectural choice, draft an ADR in docs/adr/.
- Explain non-obvious flags and settings in comments. I am learning this stack.

Where to start

In the first days, in order: a1-3 in the AWS console (including the GPU quota request, which takes time), a1-4 and a1-5 to set up WSL, VS Code and Claude Code, then a1-1 and a1-2 to create the public repo with its .gitignore and turn this plan into GitHub Issues. Then the rest of A1 and all of A2, and you have the local platform running for $0.

Decisions that keep the cost low

  • Local first. Part A runs the whole product on the laptop; AWS starts only once it works.
  • API model, no local GPU. A few dollars a month, behind a gateway that can switch providers.
  • Ephemeral environment in Part B. Destroyed every evening and rebuilt with one command. Only a tiny persistent layer stays.
  • k3s on EC2 instead of EKS. Saves about $73 a month on the control plane.
  • No NAT Gateway, no ALB. Public subnets with no inbound rules, access through SSM.
  • GPU only while running. A Spot node that comes up for a short window and shuts down, with a cost guard.
  • Spot everywhere. The k3s server and the GPU node, billed per second.
  • Observability on free tiers. Grafana Cloud and Langfuse Cloud instead of running them.
